# Spec: storage — V1

Status: proposed · Module id: `storage` · Depends on: — · Наследует [SPEC.md](SPEC.md)

## Objective

Долговечное локальное хранилище, к которому в V2 можно приставить облако, не ломая данные
пользователя. Всё остальное приложение работает только через этот слой и ничего не знает
про IndexedDB.

## Requirements

**Схема.** База `prizma`, версия 1, через `idb`. Хранилища:

| Store | Ключ | Индексы |
|---|---|---|
| `calendars` | `id` | `order` |
| `events` | `id` | `calendarId`, `start`, `uid` |
| `tasks` | `id` | `calendarId`, `due` |
| `settings` | фиксированный ключ `'app'` | — |

Индекс по `start` — тот, на котором стоит выборка видимого интервала; без него месяц
листается полным перебором событий.

**Почему у `tasks` нет индекса по `done`** (исправлено при реализации): IndexedDB допускает
в ключах только строку, число, `Date`, массив и бинарные данные. Запись с булевым значением
в индексируемом поле в индекс просто не попадёт, то есть индекс по `done` молча не работал бы.
Фильтрация по выполненности идёт в памяти — на объёмах личного списка задач это бесплатно.

**Выборка событий на интервал учитывает повторы.** Наивный диапазон по индексу `start`
пропустил бы повторяющееся событие, серия которого началась год назад. Поэтому `inRange`
берёт по индексу всё, что начинается до конца интервала, а затем оставляет: повторяющиеся —
всегда (их проверяет разворачивание), одиночные — только если пересекают интервал.

**Репозиторий.** Один модуль `src/lib/db.ts`, экспортирующий по набору операций на хранилище:
`list`, `get`, `put`, `putMany`, `remove`, `purge`. Внутри — одно открытие базы на процесс.

**Удаление — только tombstone.** `remove` ставит `deletedAt` и обновляет `updatedAt`, запись
остаётся. `list` и `get` по умолчанию скрывают записи с `deletedAt`. `purge` физически
вычищает tombstone старше 90 дней — вызывается при старте. Причина: без tombstone облако в V2
не отличит «удалено здесь» от «ещё не приходило с этого устройства» и воскресит удалённое.

**Запись проставляет метаданные сама.** `put` выставляет `updatedAt = Date.now()` и, если `uid`
пуст, генерирует его как `<crypto.randomUUID()>@prizma`. Вызывающий код про это не думает.

**Полный дамп.** `exportDump()` → JSON-объект `{ version, exportedAt, calendars, events, tasks, settings }`.
`importDump(dump, mode)` с двумя режимами: `replace` (очистить и записать) и `merge`
(по `id`, побеждает запись с большим `updatedAt`). Решение 4 в [SPEC.md](SPEC.md#resolved-decisions).

**Первый запуск.** Если `calendars` пусто — засеять: календарь «Личное» (цвет `violet`),
«Работа» (`cyan`), настройки по умолчанию из `Settings`. Признак засева — непустой стор,
а не флаг: иначе пользователь, удаливший все календари, получит их обратно.

**Заявка на зависимость:** `fake-indexeddb` (dev) — без неё тесты этого модуля в Node невозможны.
Требует одобрения по границе «Ask first».

## Success Criteria

1. `put` → `get` возвращает запись, равную записанной, с заполненными `uid` и `updatedAt`.
2. `put` без `uid` генерирует его; повторный `put` той же записи `uid` не меняет.
3. `remove` → `get` возвращает `undefined`, но запись с `deletedAt` доступна через `list({ includeDeleted: true })`.
4. `list` по индексу `start` на интервале возвращает только попадающие в него события.
5. `exportDump` → `importDump(replace)` в пустую базу даёт состояние, глубоко равное исходному.
6. `importDump(merge)` оставляет запись с большим `updatedAt` при конфликте по одному `id`.
7. `purge` удаляет tombstone старше 90 дней и не трогает свежие.
8. Засев срабатывает на пустой базе ровно один раз: второе открытие не добавляет календарей.
9. Повторное открытие базы в одном процессе не создаёт второго соединения.

## Boundaries (delta)

- **Ask first:** любое изменение схемы после первой реализации — только через bump версии
  и функцию миграции, никогда правкой `version` на месте.
- **Never:** физическое удаление записи вне `purge`.

## Out of Scope

- Шифрование хранилища — нужен ключ, а значит вопрос его хранения; V2.
- Миграции с версии 1 — писать нечего, пока версия одна.
