# Spec: Prizma Calendar — V1

Status: proposed — awaiting review

Общий фундамент инициативы. Спеки модулей (`spec/SPEC-<module-id>.md`) наследуют отсюда
tech stack, команды, структуру, стиль кода, стратегию тестов и границы — и переопределяют
только то, что у них своё. Карта модулей: [capability-map.md](capability-map.md).

## Objective

Личный календарь, в котором можно жить неделю, не открывая другой: яркий, быстрый,
работающий без сети, одинаковый в браузере, на десктопе и на телефоне.

**Пользователь** — один человек, который ведёт своё время с нескольких устройств и сейчас
держит события в чужом календаре (Google/iCloud/Outlook) и задачи в отдельном списке.

**Что значит «готово» для V1:** пользователь открывает приложение, видит свои настоящие
события из подписки на внешний календарь, добавляет к ним свои, ставит задачи с дедлайнами,
получает напоминания и может всё это унести файлом на другое устройство — без аккаунта,
без сети и без второго календаря в соседней вкладке.

| Язык | TypeScript | ^5.9.3 | `strict`, без исключений |

| Хранилище | idb | ^8.0.3 | Тонкая обёртка над IndexedDB с промисами |

**Сознательно без:** библиотеки повторов (`rrule`) — её разворачивание работает на абсолютных

сетка календаря всё равно пишется руками.

## Project Structure

```
spec/                  → Спеки: карта модулей, фундамент, по файлу на модуль
tasks/                 → План и список задач (создаётся в Phase 2)
src/lib/               → Чистая логика без React: время, повторы, ICS, хранилище
src/store/             → zustand-стор и селекторы
src/components/        → React-компоненты, сгруппированные по виду
src/styles/            → Токены темы
test/                  → Тесты на src/lib (node:test, без браузера)
public/                → Иконки, favicon
src-tauri/             → Обёртка десктопа (shell-desktop)
```

Границы модулей из карты живут в `src/lib` как отдельные файлы, а не как папки: модуль —
это единица спеки и ревью, а не обязательно каталог. `calendar-core` — это
`datetime.ts` + `recurrence.ts` + `occurrences.ts` + `types.ts`.

## Code Style

Реальный фрагмент из `src/lib/datetime.ts` — так выглядит код, который считается готовым:

```ts
/** Calendar-day arithmetic: the time of day is preserved exactly. */
export function addDays(local: Local, days: number): Local {
  const p = parse(local)
  const d = new Date(p.y, p.m - 1, p.d + days, 12) // noon avoids DST edges
  return formatParts({ ...p, y: d.getFullYear(), m: d.getMonth() + 1, d: d.getDate() }, !hasTime(local))
}
```

Конвенции, которые из него видны:

- **Именованные экспорты**, без `default` — кроме React-компонентов.
- **Чистые функции в `src/lib`**: ни `window`, ни React, ни стора. Поэтому они тестируются в Node.
- **Комментарий объясняет «почему», а не «что»**: `// noon avoids DST edges` — это та строка, которую
  иначе уберут как лишнюю и получат баг дважды в год.
- **Типы-алиасы для доменных строк** (`Local`, `LocalDate`) вместо голого `string` в сигнатурах.
- `camelCase` для значений, `PascalCase` для типов и компонентов, `SCREAMING_SNAKE` для констант-пределов.
- Никаких `any` и `as` для обхода типов; `strict` и `noUnusedLocals` включены и не отключаются.
- **Только стираемый синтаксис TypeScript.** Node срезает типы, но ничего не генерирует,
  поэтому `enum`, `namespace` и parameter properties (`constructor(private x: T)`) ломают
  прогон тестов. Поля класса объявляются и присваиваются явно. Обнаружено на `FeedError`
  в задаче 15.
- Комментарии к коду — по-английски, тексты интерфейса и спеки — по-русски.

## Testing Strategy

**Фреймворк:** встроенный `node:test` + `node:assert/strict`. Без Vitest и Jest: вся логика,
которую стоит покрывать, чистая и не нуждается в браузере или трансформере.

**Где лежат:** `test/<module>.test.ts`, по файлу на модуль `src/lib`.

**Что покрывается тестами обязательно** — то, где ошибка тихая и дорогая:

| Модуль | Приоритет | Почему |
|---|---|---|
| `calendar-core` (повторы) | Обязательно | Ошибка в RRULE даёт сдвиг или пропуск события, который замечают через месяцы |
| `ics-sync` (разбор) | Обязательно | Чужие файлы приходят в десятке вариантов экранирования и переноса строк |
| `storage` | Обязательно | Потеря данных необратима; нужен прогон круга put → get → удаление → экспорт → импорт |
| `tasks`, `reminders` | Нужный минимум | Логика проще, но расчёт «за сколько до» и просроченность стоит закрепить |
| `ui` | Не покрывается | Проверяется руками в браузере по чек-листу из `SPEC-ui.md` |

**Уровни:** только модульные. E2E в V1 нет — цена поддержки выше пользы на одном разработчике.

**Правило на каждый баг:** сначала падающий тест, потом исправление.

## Boundaries

**Always do**

- Запускать `npm test` и `npm run typecheck` перед тем, как назвать задачу выполненной.
- Хранить время как «настенное» (`2026-11-22T09:30`, без смещения и без `Z`).
- Удалять через tombstone (`deletedAt`), а не физически — иначе облако в V2 не сможет разнести удаление.
- Присваивать каждой записи iCalendar `uid` при создании.
- Говорить, что именно осталось непроверенным, если проверить не удалось.

**Ask first**

- Любая новая зависимость. В V1 уже известны две заявки: `fake-indexeddb` (тесты `storage`)
  и `@capacitor/*` + `@tauri-apps/cli` (обёртки платформ).
- Изменение схемы IndexedDB после первой реализации — нужна миграция, а не правка версии.
- Любой сетевой запрос к новому хосту.
- Расширение V1 за границы, записанные в карте.

**Never do**

- Отключать тест, чтобы получить зелёный прогон; падающий тест либо исправляется, либо удаляется с объяснением.
- Складывать секреты, токены или OAuth-ключи в репозиторий.
- Отправлять данные пользователя куда-либо, кроме URL ленты, которую он сам добавил.
- Молча расширять V1 идеей, пришедшей по ходу: она идёт в Out of Scope карты.
- Хранить абсолютные моменты (`Date`, epoch) как время события.

## Success Criteria

V1 готов, когда всё перечисленное проверяемо верно:

1. `npm run build` и `npm run typecheck` проходят без ошибок и предупреждений TypeScript.
2. `npm test` зелёный, и в нём есть тесты на повторы, разбор ICS и круг сохранения в `storage`.
3. В браузере: месяц, неделя, день и список открываются, переключаются и показывают одни и те же события.
4. Событие создаётся кликом по сетке, переносится и растягивается мышью, правится и удаляется.
5. Повторяющееся событие разворачивается верно, и у него можно изменить одно вхождение,
   не затронув остальные.
6. Задача с дедлайном видна рядом с событиями того дня и отмечается выполненной.
7. Напоминание приходит уведомлением, когда приложение открыто.
8. Подписка на внешнюю ICS-ссылку добавляется, её события появляются в сетке и помечены как
   «только чтение»; повторное обновление не создаёт дублей. **В вебе проверяется на ленте с
   разрешающим CORS**; для лент Google и iCloud в вебе ожидается понятная ошибка с предложением
   импортировать файлом, а работа по ссылке появляется в обёртках платформ — см. раздел про CORS
   в [SPEC-ics-sync.md](SPEC-ics-sync.md#requirements).
9. Экспорт `.ics` открывается в Google Calendar без ошибок; экспорт полного дампа и его импорт
   восстанавливают состояние один в один.
10. После первой загрузки приложение открывается и работает при выключенной сети.
11. Приложение устанавливается как PWA и запускается отдельным окном.
12. `src-tauri/` и `capacitor.config.ts` присутствуют с инструкцией сборки в `README.md`.

## Resolved decisions

Четыре вопроса, оставшихся открытыми в карте, закрыты так. Это решения по умолчанию,
а не согласованные — любое меняется на ревью.

1. **Синхронизация в V1 = подписка + файл.** Односторонняя: ленту читаем, свои события пишем
   только в локальные календари. Пункт «синхронизация» считается выполненным по критерию 8.

   **Обнаружено при написании спеки и это важно:** браузер не даст прочитать ленту Google или
   iCloud напрямую — на этих хостах нет заголовка CORS. То есть в чистом вебе подписка именно
   на твой Google-календарь не заработает, останется импорт файлом. По ссылке она начинает
   работать в обёртках десктопа и мобильных, где запрос идёт нативно. Это переводит
   `shell-desktop` и `shell-mobile` из «приятного дополнения» в условие того, чтобы выбранный
   тобой пункт про синхронизацию был выполнен по-настоящему, и поднимает их приоритет в плане.
2. **Задачи и в сетке, и панелью.** Задача с дедлайном показывается в строке «весь день» того дня,
   полный список — в боковой панели. Переключатель «показывать задачи в сетке» в настройках, по умолчанию включён.
   Причина: в сетке они живее и их видно в контексте дня, но без выключателя загромождают день у того,
   у кого задач много.
3. **Светлая тема входит в V1.** Tailwind 4 задаёт тему CSS-переменными, поэтому второй набор
   классов не нужен и цена заметно ниже прежней оценки. Тёмная — по умолчанию.
4. **Полный дамп базы входит в V1.** Без облака это единственный способ перенести данные между
   устройствами, так что для офлайн-первого приложения это не удобство, а необходимость.
